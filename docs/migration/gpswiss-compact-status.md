# Status operacyjny po #1514

Między `local_retry_state_reset` a `status_loaded` dotychczas wykonywano GET `/admin/tools/gpswiss-migration-export/UUID`. Audyt potwierdził wywołanie pełnego `BrowserMigrationExport::status()` i `BrowserMigrationSnapshot::index()`: PHP czytało i dekodowało cały checkpoint zawierający rosnącą listę shardów. Do odpowiedzi trafiały metadane wszystkich datasetów. Sama lista shardów nie była jednak serializowana w `snapshot_progress.datasets`; nie utożsamiamy wzrostu wewnętrznego checkpointu ze wzrostem bajtów odpowiedzi ani nie przypisujemy bez logów konkretnego produkcyjnego `network_error` do OOM/timeoutu.

Runner używa teraz wyłącznie GET `.../UUID?format=compact` do odczytu statusu, także po błędzie, przy reloadzie i ręcznym Wznów. Discovery używa `...?format=compact`. Odpowiedź ma ścisłą listę pól operacyjnych i limit 8192 bajtów. Nie zawiera datasetów, manifestów, raportów, photo_results, rekordów ani listy plików do pobrania. `status_response_bytes` odpowiada rzeczywistej liczbie bajtów JSON. Pełny status pozostaje pod osobnym linkiem operatora (`format=status`); lista archiwów jest pobierana raz po ukończeniu (`format=artifacts`). Autoryzacja właściciela i private/no-store pozostają obowiązkowe.

Postęp operacyjny jest zapisywany do osobnego, prywatnego, pochodnego `compact-snapshot-progress.json`. Cache jest związany z attemptem i fingerprintem atomowo zapisanego checkpointu (dev/inode/size/mtime/ctime). Nie jest źródłem danych eksportu ani podstawą przesuwania kursora. Nowe ticki publikują go po zatwierdzeniu checkpointu; nie dodają pól do danych snapshotu i nie zmieniają granic ani formatu v3.

Dla już istniejącej próby bez cache pierwszy compact GET odczytuje plik strumieniowo: zachowuje wyłącznie metadane operacyjne, a duże tablice shardów pomija bez ich dekodowania/materializowania. Może przeczytać cały plik jeden raz, ale nie tworzy pełnego indeksu w pamięci. Kolejne odczyty sprawdzają fingerprint i czytają mały cache. Uszkodzony cache jest odtwarzany; niepełny plik diagnostyki nie blokuje zdrowego checkpointu. Brak możliwości zapisu cache nie zmienia źródłowych danych, lecz wymaga ponownego odczytu strumieniowego.

Żądanie statusu ma osobny timeout 10 s i maksymalnie cztery próby z backoff 250/500/1000 ms. Błąd transportu, malformed JSON, timeout, 500/502/503/504 prowadzą najpierw do ponownego compact GET, a nie nowego snapshotu. Po wyczerpaniu zwracany jest `status_fetch_retry_exhausted` bez mnożenia retry przez zewnętrzną pętlę. 401/419 zatrzymują runner i wymagają loginu/reloadu. Po sukcesie statusu zdrowy snapshot_running/snapshot_tick uruchamia tick tej samej próby.

Diagnostyka klienta rozróżnia `request_kind=status`, `compact_status`, dokładny endpoint/route, HTTP, czas, bajty, Content-Length (jeśli jest), Content-Type, malformed JSON, timeout i bezpieczny typ wyjątku transportu. Nie pokazuje body ani nagłówków autoryzacji. Backend dodaje czas statusu, safe reason i klasę wyjątku bez message/stack/SQL. Obsługa shutdown dla compact GET zapisuje best-effort `backend_timeout`, `memory_exhaustion` albo `php_fatal_error` do osobnego prywatnego pliku; SIGKILL i błąd przed wejściem do kontrolera nie gwarantują takiego zapisu. TypeError fetch sam nie dowodzi connection reset — pozostaje unknown transport error.

Testy przy 0, 20568 i 79000 rekordach oraz dużym syntetycznym indeksie potwierdzają stały budżet odpowiedzi, brak struktur danych, odtwarzanie cache i niezmienność hashy checkpointu. Chromium odtwarza run `8de6e27c-ad7c-470b-830b-b9ecee9446ba`, attempt `9cb33c92-3f1e-4db0-b08d-052715aa5f4c`, marketplace_category_mappings / cursor2777 / processed20568. Pierwszy błędny status GET, retry, udany GET i tick prowadzą do cursor2782 / processed20573, bez Start/Retry snapshotu i bez zmiany attemptu.

Po wdrożeniu: odświeżyć panel i kliknąć **Wznów istniejący eksport**. Nie używać Ponów snapshot. Nie wykonywano produkcyjnego eksportu, nowych prób, importu ani operacji na providerach. Wszystkie zmiany plików podczas testów dotyczyły lokalnych fixture; istniejące dane i granice produkcyjnego snapshotu pozostają nietknięte.
