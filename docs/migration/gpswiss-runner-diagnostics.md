# Runner po #1512: zachowanie istniejącego checkpointu

Kod #1512 zamieniał wszystkie wyjątki obsługi fetch na `network_error`, ukrywając timeout i błąd parsowania. Nie ma produkcyjnych logów ani dostępu do checkpointu, więc same zgłoszone objawy nie rozstrzygają przyczyny zatrzymania przy 2528/79957. Nie uruchamiano produkcyjnego eksportu ani nowej próby.

Po wdrożeniu operator odświeża panel i klika **Wznów istniejący eksport** dla `8de6e27c-ad7c-470b-830b-b9ecee9446ba`. Nie używa Ponów snapshot. Run, attempt, granice i niezmienne porcje pozostają. Nowe porcje mają limit 5 rekordów; weryfikacja istniejących porcji zachowuje ich pierwotny rozmiar i sumy.

Przejściowe błędy transportu, timeout, malformed JSON oraz 408/429/500/502/503/504 prowadzą do backoff i odczytu statusu. Dopiero udany odczyt statusu pozwala ponowić tick. Jeśli poprzedni tick zapisał checkpoint mimo utraty odpowiedzi, pętla używa nowego kursora. Pięć nieudanych ticków **bez potwierdzonego postępu checkpointu** kończy pętlę z `retry_exhausted`; także po piątym błędzie najpierw odczytywany jest status. Status poll ma osobny limit czterech odczytów. 401/419 wymagają loginu/reloadu, 403 i trwałe blokady nie są ponawiane. Nie są ponawiane automatycznie Start ani Retry snapshotu.

Panel pokazuje bieżącą diagnostykę, osiem ostatnich błędów oraz osobne `last_operation_failure`: endpoint/action, HTTP, czas, otrzymane bajty, timeout, bezpieczny typ wyjątku, safe reason i kursor. Dla nieudanego ticka zapisuje też checkpoint przed requestem i po recovery poll, numer próby oraz checkpoint_progress_detected. Udany GET statusu ani ręczne Wznów nie kasują tej historii w otwartej stronie; Wznów resetuje lokalny budżet i harmonogram. Historia nie jest utrwalana po przeładowaniu strony. Nie pokazuje body, nagłówków, CSRF, komunikatu wyjątku ani stacktrace. Fetch udostępnia zwykle tylko TypeError dla resetu połączenia, DNS, TLS i innych problemów transportu; bez dowodu przeglądarka oznacza je jako `unknown_network_error`, zamiast udawać rozpoznanie resetu.

Backend zapisuje prywatny `last-tick.json` przed snapshot tickiem i po zatwierdzeniu checkpointu: dataset, kursory, limit/attempted/completed, czas i klasę wyjątku bez message/SQL/stack. Rozpoznane timeouty zapytania i krytyczny limit PHP mają `backend_timeout`. Shutdown jest best effort; SIGKILL nie wykona handlera. Pozostawione `tick_running` z wolną blokadą wskazuje niedokończony zapis diagnostyki lub przerwanie procesu, bez rozstrzygania konkretnego limitu hostingu. Diagnostyka nie jest źródłem postępu i nie trafia do paczki migracyjnej.

Nieznany przejściowy wyjątek backendu zachowuje ostatni zatwierdzony stan do replay. Wykryta zmiana źródła/schematu/sumy nadal blokuje próbę; nie jest traktowana jako błąd sieci. JSON odpowiedzi snapshot_tick zawiera postęp i diagnostykę, bez listy wszystkich datasetów ani danych produktów. Źródłowe dane biznesowe, providerzy, integracje i architektura logicznego snapshotu pozostają bez zmian.

## Postęp po HTTP 500 podczas artifact preflight (#1519)

Zgłoszony status: ten sam run `8de6e27c-ad7c-470b-830b-b9ecee9446ba`, attempt `9cb33c92-3f1e-4db0-b08d-052715aa5f4c`, generation=1, preflight=45/1296, next_action=snapshot_tick, busy=false. `last_tick` potwierdza zatwierdzony artifact_preflight 40→45 w 268 ms. To dowód postępu backendu, nie identyfikacja żądania, które zwróciło HTTP 500. Bez jego odpowiedzi lub logów hostingu nie rozstrzygamy przyczyny tego 500. W kontrolerze obsługa POST ma `ignore_user_abort(true)`; ukończenie checkpointu i dojście odpowiedzi do przeglądarki są oddzielnymi zdarzeniami. Błąd może wystąpić także po zapisie ticka, przy budowie odpowiedzi lub poza PHP. Nie przypisujemy starej klasy wyjątku z last_tick do bieżącego HTTP 500.

Root cause zatrzymania JS: `drive()` zerowało `attempts` tylko w udanej gałęzi POST. `recover()` odczytywało aktualny status, ale nie porównywało go z checkpointem sprzed requestu i nie zerowało licznika po postępie. Kolejne utracone odpowiedzi sumowały się mimo przesuwania preflight. Przy piątym błędzie `if (++attempts > 4) throw` pomijało nawet status poll. Artifact preflight korzystało z tej samej gałęzi co export/verify — nie miało osobnego mechanizmu retry, który można byłoby naprawić niezależnie.

Ta sama istniejąca ścieżka recovery porównuje teraz semantyczny checkpoint: run/attempt, phase/dataset, generation/boundary, offset preflight, cursor, processed/exported/verification oraz rundę reconciliation. Nie używa samego fingerprintu, mtime, czasu statusu, busy ani starej diagnostyki jako dowodu postępu. Zmiana runu/attemptu, znanej granicy/generacji w tym samym datasecie albo cofnięcie preflight blokuje lokalną pętlę. Status failed/blocked nie potwierdza zdrowego postępu. Przy postępie runner emituje `checkpoint_progress_detected`, `retry_counter_reset`, a następny przebieg `tick_scheduled`. Przy braku postępu zachowuje budżet tego checkpointu i stosuje dotychczasowy backoff/status poll. Piąty błąd kończy pętlę dopiero po sprawdzeniu statusu.

Backendowy preflight, pięć shardów na tick, run/attempt, generation=1, boundary, offset i chain pozostają bez zmian. Po deployu odświeżyć panel i użyć **Wznów istniejący eksport**, od 45/1296 lub nowszego zatwierdzonego checkpointu. Nie uruchomiono produkcji ani nowej próby.

Chromium testuje 40→45 i siedem kolejnych utraconych odpowiedzi z postępem, postęp dopiero po piątym błędzie, pięć realnych błędów przy 45 i ręczne Wznów, reload/double-click, HTTP 500/502/503/504, timeout/network/malformed JSON, busy, fingerprint-only, trwałą blokadę, identity/boundary mismatch i 419. Te same przypadki postępu działają dla export i verification. Mocki sprawdzają brak nowych runów/attemptów/generacji, brak powtórnego commitowania checkpointu oraz zachowanie bezpiecznej diagnostyki bez message/stack/secrets. Nie są to wywołania produkcji ani syntetyczny eksport zastępujący rzeczywiste dane.
